# GOAL

用戶視角證據 v1（使用者 2026-08-05 核定；同日缺點分析後修訂——產量併列防收縮遊戲、
門檻與趨勢語義、新鮮度窗、破門檻才告警）——為艦隊產品建立「用戶視角」的機械化證據管線，
回答「產品真的變好了嗎」而非「測試綠了幾個」。v1 兩個真值鏡頭：
（一）**gooaye 真值對帳**：從 gooaye repo（唯讀）抽樣已標 verified 的數值 claim N≥20 筆，
逐筆回查原始逐字稿座標，機械比對數值／單位／指涉，輸出正確率＋逐筆證據對照。
**產量併列鐵律（防收縮遊戲化）**：報告必須同排呈現「本期 verified 總量、入隊待複核量、
偵測總量」三數與其週環比——正確率上升伴隨產量萎縮須自動標記「疑似收縮刷分」告警。
（二）**taiwan-intel 真值探針**：抓取線上站台公開 JSON，**只抽發佈時間 24 小時內的事件**
（新鮮度窗——防把來源網頁漂移誤計為管線錯誤）N≥20 筆：(a) 來源 URL 可達性；
(b) judge 端點比對摘要與來源頁內容一致性（每筆保存兩側原文摘錄）；(c) 時間／地理欄位
內部一致性。同樣併列站台事件總量與週環比。
**門檻與趨勢語義（分數→證據的必要條件）**：兩鏡頭各設預設門檻（gooaye 正確率 <90%、
taiwan-intel 一致率 <85%，config 可覆寫）與趨勢規則（連兩期環比惡化 >5pp）；
未破門檻＝只在 digest 留一行分數；破門檻或趨勢惡化＝告警並附**最異常 3 筆樣本**
（不是全表——使用者的稽核預算是每週 10 分鐘，不是讀報告）。
產出：`scripts/user-evidence/` 可重跑 runner → `docs/user-evidence/<ship>-<YYYYMMDD>.md`
（機械分數、抽樣 seed、三量併列、逐筆證據）＋ `docs/user-evidence/latest.json`
（機器可讀最新指標，供巡檢與 digest 消費）。

## 驗收指令

```sh
npx vitest run tests/user-evidence --reporter=dot
```

## 細部要求

1. **觀測隔離鐵律**：只觀測、永不接入任何 verify／review 閘（防 Goodhart）；報告不得寫入
   任何 USER-SIGNALS.md（方向盤主權屬使用者）；對船 repo 一律唯讀。
2. 抽樣顯式 seed 記入報告（可重現）；judge 判定每筆必附兩側原文摘錄（人工可稽核）。
3. 網路呼叫僅限 taiwan-intel 公開站台 JSON 與其引用來源 URL（逾時／重試上限明確，
   失敗標 unreachable 且**不計入一致率分母**——可達性另列一欄）；gooaye 鏡頭零網路。
4. tests/user-evidence*.test.ts 先紅後綠覆蓋：(a) 報告格式（分數、seed、三量併列、逐筆
   證據、latest.json）；(b) 同 seed 重跑一致；(c) 新鮮度窗過濾（>24h 事件不入樣本）；
   (d) 收縮刷分偵測（正確率↑且產量↓>30% 觸發標記）；(e) 門檻／趨勢告警判定（未破＝
   digest 一行、破＝告警＋top3 異常樣本）；(f) 對船 repo 唯讀驗證；(g) 實跑產出兩船首份
   真實報告並通過格式驗證。
5. kernel 頂層零增長；`npm run build` 與既有測試零改動全綠。

## 邊界

- 不改 configs/*.json、不動 daemon、不碰船 repo 工作樹；報告目錄只增不改寫歷史。
- **v2 掛帳（本 GOAL 明知不做的架構債）**：(a) 價值鏡頭——正確率是衛生指標不是價值指標，
  「值得嗎」需盲測偏好面板，待審查者金標校準集（已立案）落地後另立 GOAL；(b) judge
  獨立性——本 GOAL 的比對仍用艦隊 judge 單點，多模型面板屬 v2；(c) 行情回測、
  note-filler／PA 鏡頭、可用性（能用嗎）鏡頭皆屬後續。
