> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:test-driven-development. Each task = 寫失敗測試 → 確認 FAIL → 實作 → 全套綠 + typecheck → commit。

**Goal:** 閉環驗收 6 條全過（spec L54-59）：使用者往 voice-actress `BACKLOG-adng.md` 加真任務 → 30 分內撿起 → worktree 執行 → verify 過 → judge MATCH → 合回 master → Discord 收到通知含 commit hash 與成本 → backlog 空則 idle → 72h 浸泡無殭屍/心跳不斷/日摘要每天到。

**Architecture:** kernel 硬前置修復（Task 1-5）→ worktree 執行環境（Task 6）→ voice-actress 接線（Task 7）→ soak 補強（Task 8）→ 排程自啟（Task 9）→ 72h 浸泡（Task 10）。Task 1-6 互相獨立可亂序，Task 7 依賴 6，Task 9 依賴 7。

**Tech Stack:** 同 M1-M3b（TypeScript/Node、vitest、better-sqlite3、zod）。新增面：git worktree 操作、Windows Task Scheduler。

### Task 1: lock.ts——PID-in-lock + steal 前驗活（HIGH-1，respawn 接線前硬前置）

**Files:**
- Modify: `src/lock.ts`, `tests/lock.test.ts`, `tests/lock-errors.test.ts`

**Interfaces:**
- `acquireLock(dir, staleMs?)` 簽名不變。行為變更：
  - mkdir 成功後在 `dir/pid.json` 寫 `{ pid: process.pid, startedAt: <ISO> }`（tmp+rename 原子寫，比照 events.ts 慣例）。
  - stale 判定改三段：(1) 讀 `pid.json` 成功且該 PID **存活** → 直接 return false（不看 mtime——修「假 stale」：長任務 30 分不更新 mtime 被誤搶）。驗活用 `process.kill(pid, 0)` try/catch（EPERM=活著、ESRCH=死了）。(2) PID 死了 → 走既有 rename 原子搶奪（不等 staleMs——修「假 fresh」：崩潰後 30 分內鎖佔著茅坑）。(3) `pid.json` 缺失/損壞 → fallback 既有 mtime 年齡判定（staleMs 語意保留）。
  - steal 成功重建 mkdir 後同樣寫入自己的 `pid.json`。
- `releaseLock` 不變（rmSync recursive 已涵蓋 pid.json）。
- 已知限制記報告：PID recycling 理論可能誤判活著（Windows PID 重用）——`startedAt` 欄位先寫入但本任務不做 creation-time 比對，記 ledger 可延（真實風險窗=崩潰後恰好 PID 被另一長壽進程佔用，機率低且 fail-safe 方向=不 steal）。

**Steps:**
- [ ] **Step 1: 寫失敗測試**——(a) 鎖存在+pid.json 指向存活進程（用 process.pid 自己）+mtime 極舊 → acquire 返回 false 不 steal；(b) 鎖存在+pid.json 指向死 PID（spawn 完即死的子進程 pid 或保證不存在的大 PID）→ 立即 steal 成功且新 pid.json 是自己；(c) pid.json 損壞（非 JSON）→ fallback mtime：新鮮不 steal、超過 staleMs 可 steal；(d) 既有測試逐字不動全綠。
- [ ] **Step 2: 跑確認 FAIL**
- [ ] **Step 3: 實作**
- [ ] **Step 4: 全套綠 + typecheck，Commit**

```bash
git add -A && git commit -m "fix(m4): lock——PID-in-lock 驗活取代純 mtime 判 stale（HIGH-1）"
```

**Interfaces:**

  - `prepareWorktree(projectPath, worktreesDir, taskId): { cwd, branch }`——`git worktree add -b adng/<taskId> <worktreesDir>/<taskId> HEAD`；若分支/目錄殘留（前次崩潰）先 `git worktree remove --force` + `git branch -D` 清掉重建；成功後在 worktree 根寫 `.adng-worktree` marker 檔（verifier rollback 守門的正是它）。
  - `mergeBack(projectPath, branch): { merged: boolean, commitHash?: string }`——在主 repo `git merge --ff-only adng/<taskId>`；ff 不可行（使用者同時動了主分支）→ 回 `{merged:false}` 不硬 merge（呼叫端告警+保留分支給人工，任務標 blocked 附 reason）。
  - `cleanupWorktree(projectPath, worktreePath, branch)`——`git worktree remove` + `git branch -d`（成功合回後呼叫；失敗路徑**保留現場**供 debug，但 events 記 `worktree-kept` 事件讓 digest 可見）。
- scheduler 接線：pick task 後 prepareWorktree → job.cwd=worktree、job.directive 尾附 extraDirective → engine.run → verifier（在 worktree 內跑 verify/rollback——marker 已在）→ ok 則 mergeBack：merged → cleanup+report done（通知含 mergeBack 的 commitHash）；ff 失敗 → report blocked（reason=merge-conflict）+告警。engine 失敗/verify 拒 → 既有流程（rollback 已在 worktree 內安全），cleanup 保留現場。
- mock engine 劇本需能在 worktree 內產生真 commit（測試用臨時 git repo：mkdtemp + `git init` + 初始 commit；絕不碰真專案）。
- 非 git 專案（`git rev-parse` 失敗）→ prepareWorktree 上拋，scheduler 歸 blocked+告警（fail-open 不炸 daemon）。

- [ ] **Step 1: 寫失敗測試**——(a) prepare 建出 worktree+分支+marker；(b) 殘留現場重建成功；(c) 引擎在 worktree commit → mergeBack ff 成功、主 repo HEAD 前進、worktree 清掉；(d) 主 repo 被第三方推進一格 → mergeBack 回 merged:false、分支保留；(e) scheduler e2e：mock engine + 臨時 repo 全鏈路 done；(f) 非 git 目錄 → blocked。
