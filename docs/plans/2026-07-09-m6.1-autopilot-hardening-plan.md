# M6.1 autopilot 生產化 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** 把 GOAL autopilot 從 sandbox-v1 推向「可無人值守」——補上停機 Discord 告警（opus 全分支審查標的唯一硬閘 I2），並消除多輪重複 append 任務的 backlog 污染（reviewer hygiene 項）。

**Architecture:** 兩處都在 `src/autopilot/`（run.ts 停機告警、orchestrator.ts append 去重），**零 kernel 改動**。複用 `assemble()` 已回傳的 `notifier`（`DiscordNotifier.send`）與現有 `Notifier` 介面/`FakeNotifier` 測試模式。

**Tech Stack:** TypeScript / Node / vitest。

## Global Constraints

- **零 kernel 改動**：只動 `src/autopilot/run.ts`、`src/autopilot/orchestrator.ts` 與其測試。`wc -l src/*.ts` 維持 2427（不得增）。
- **`src/autopilot/` 各檔 ≤200 行**。
- **鐵律 #4 fail-open**：告警失敗不得中斷/反殺——`notifier.send()` 本身永不 throw（回 false 寫 DLQ），呼叫端也不得因告警失敗而 throw。
- **告警一次性**：停機（`no-progress`/`stuck`/`killed`）是 one-shot（`main()` 結束前發一次），**不接冷卻閘**（那是 daemon 24/7 loop 用的）。`achieved` 不告警。
- **每 task 收尾必跑 `npm run build`（tsc 零錯誤）＋ `npx vitest run` 全綠**（M6 教訓：vitest 的 esbuild 跳 strict null，只有 tsc 抓得到）。
- LF 換行；conventional commit；每 task commit；SDD 雙判定審查。

export function stopAlertMessage(goalId: string, outcome: GoalOutcome): string | null {
  if (outcome.kind === 'achieved') return null
  const base = `autopilot GOAL 停機（goal ${goalId}）：${outcome.kind}，共 ${outcome.rounds} 輪`
  return outcome.kind === 'stuck' ? `${base}——${outcome.reason}` : base
}

### Task 2: append 去重——orchestrator 跳過本 session 已 append 過的任務文字（`src/autopilot/orchestrator.ts`）

**Files:**
- Modify: `src/autopilot/orchestrator.ts`
- Test: `tests/autopilot-orchestrator.test.ts`（加 describe/test）

**Interfaces:**
- Consumes: 既有 `runGoalSession`、`OrchestratorDeps`（`kernelDeps.store.append`）。
- Produces: 無新匯出；行為變更——同一 GOAL session 內，相同任務文字只 append 一次。

**背景**：多輪 no-progress 時 planner 常重複產出相同任務；每輪照 append 會讓 backlog 累積重複 autopilot 行（且重跑已 blocked 的失敗任務無益）。以 session 內記憶體 `Set<string>` 記錄「已 append 過的文字」，重複者跳過（不 append、不入 history）。跨狀態正確（不論該任務後來 done/blocked，同文字都不再 append）。

- [ ] **Step 1: 寫失敗測試** — `tests/autopilot-orchestrator.test.ts` 加（沿用該檔既有 `base()`/mock 模式；planner 連兩輪回同一任務、evaluator 恆不達成以逼出多輪、`noProgressLimit` 設 2）：

```ts
test('append 去重：同 session 相同任務文字只 append 一次', async () => {
  const appended: string[] = []
  const deps = base({ objective: 'o', noProgressLimit: 2 }, {
    planFn: async () => ({ kind: 'tasks', tasks: ['重複任務甲'] }), // 每輪都回同一條
    evalFn: async () => ({ achieved: false, score: 1, detail: '' })  // 恆不進步 → 多輪
  })
  const realAppend = deps.kernelDeps.store.append.bind(deps.kernelDeps.store)
  deps.kernelDeps.store.append = (t: string, o: { goalId: string; round: number }) => { appended.push(t); realAppend(t, o) }
  const out = await runGoalSession(deps)
  expect(out.kind).toBe('no-progress')                 // 仍正常終止
  expect(appended.filter(t => t === '重複任務甲')).toHaveLength(1) // 只 append 一次
})
```
（`base()` 是該測試檔既有的 helper，建立含真 `BacklogStore` 的 `OrchestratorDeps`；若既有 `base()` 簽名不同，依實際簽名調整——實作者須先讀該檔既有測試。）
