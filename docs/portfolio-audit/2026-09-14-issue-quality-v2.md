# Issue Quality v2：先確認問題，再決定最小工作

生效：2026-09-14。來源：使用者要求優化既有稽核／競品排程，避免優先級膨脹、過度工程及研究項目被直接實作。

適用於產品董事會、固定 50-Persona Audit、外部競品雷達的 Issue 產生與再分流。不建立新 GOAL、不更改產品程式、執行器、CI、部署、權限或 secrets。這是排程與追蹤規則，**不是已實作的執行器強制控制**。

`2026-09-06-50-persona-audit.md` 的固定 A01–J05、嚴重度與全部 CLEAN 條件保持不變；本文件校準開單與工作範圍，不以降級或研究分類掩蓋真正缺陷。

## 1. 分開記錄：問題類別、影響、工作次序與實作資格

- `BUG`：目前受支援流程有具體可到達的契約違反；可由決定性的原始碼路徑或實際執行證明。須分開標示 SOURCE_CONFIRMED 與 EXECUTED_REPRODUCTION，不能互相冒充。
- `VALIDATION_GAP`：缺少執行證據、CI 不執行或必要測試未納入驗證。缺證據不等於產品壞了；實際排程同步停擺、必要發布被阻塞則依已證明的核心影響另行分級。
- `MAINTENANCE`：改善維護／文件但未證明顯著任務失敗。
- `RESEARCH`：問題原因、需求或解法仍需驗證；必須提出有邊界的研究問題、最小實驗與 BUILD / NARROW / REJECT 決策條件。
- `OPPORTUNITY`：新增能力的價值假設；競品存在不代表本專案需要。

影響嚴重度遵守原規範。P0/P1 必須說明誰在何種受支援條件下遭遇資料／權限／核心任務風險及可到達的因果鏈；不需等待真實事故才處理安全缺陷，也不可只靠想像升級。P2 必須說明顯著的完成率、恢復性或維護流程影響；一般改善依 P3。研究急迫性另列 `decision_priority`，不得把「P1 Research」混成已證實 P1 缺陷。

實作資格：`NEEDS_EVIDENCE | NEEDS_REVIEW | READY_FOR_IMPLEMENTATION | DEFERRED`。新 Issue 預設不授權自動實作。只有已确认範圍、最小解法、有效證據、驗收、依賴與既有使用者授權均具備時，才能記錄 READY；READY 仍不是 merge／deploy／付費／外部寫入授權。

可用精簡 metadata 區塊：
```yaml
issue_quality_version: 2
kind: BUG | VALIDATION_GAP | MAINTENANCE | RESEARCH | OPPORTUNITY
severity: P0 | P1 | P2 | P3 | NOT_ESTABLISHED
evidence: SOURCE_CONFIRMED | EXECUTED_REPRODUCTION | NEEDS_EVIDENCE
triage: NEEDS_EVIDENCE | NEEDS_REVIEW | READY_FOR_IMPLEMENTATION | DEFERRED
auto_implementation: false
```
不要求建立新標籤、資料庫或驗證框架才能使用本規則；沿用既有標籤，沒有時以正文記錄。

## 2. 最小修正先於大型架構

每個 candidate 在開單前回答：目前誰受影響、具體失敗／人工步驟、既有功能能否解決、不做的後果、最小有效修正、為什麼不是更小的改法、額外維護／成本／權限風險。

先比較不改程式／修正文件、重用既有功能、局部修補，再考慮新模組或架構。新增資料庫、ledger、registry、狀態機、跨專案 framework、雲端服務或多平台矩陣，須逐項說明必要性與被否決的小方案。名稱像框架不算價值證據；安全缺陷也不能用「簡單」作為省略必要邊界的理由。

不得把候選大型解法寫成缺陷根因。例如根因應是「apply 重新搜尋而未保留已選 video ID」，不是「沒有 canonical resolution ledger」。fingerprint 以實際行為／根因去重，換架構名不能重開一張。

Issue 只要求修復本根因所需的驗收。無關的配額儀表板、完整 OAuth 改造、全平台移植、競品功能等移至非阻塞備註；不自動拆出一批新工單。拆單須有独立價值及交付邊界。研究不是高成本方案的預先批准。

## 3. 開單門檻與報告長度

保留所有通過校準門檻的有效 findings，不設任意數量上限；**允許一輪零新 Issue**。沒有可檢驗問題／合理收益的點子只留研究清單，不為了寫入閉環硬立案。

簡單修復預設一個根因、一項最小變更、約 3–5 個直接驗收條件，必要安全例外可增加。正文讓實作者快速看懂：問題／證據、影響與分級、最小修法、不做什麼、驗收與回歸、狀態／依賴。完整競品、50 Persona、董事會與反方論述保留在 linked audit，不逐張複製。

模型扮演 50 個 persona 或多位主管仍是合成推演，不是 50 位獨立受試者或獨立審查。反方必須檢查既有解法、替代根因、環境限制、產品規模與過度工程，不只重述支持意見。沒有真正獨立執行者時不得宣稱 independent validation。

Opportunity Score 若保留，必須附各項依據與未知，不用 92/94/98 等精確高分替代資料；不足時用定性判断。不能從合成偏好／受影響人數推算真實發生率、營收或優先級。

## 4. 執行證據按路徑，不按品牌

有效本機、隔離容器、CI 或部署執行都可支持其真正覆蓋的路徑；記錄 SHA、指令／run、時間、環境、結果及限制。實際本機測試不是紙上推演，但也不能证明未執行的雲端身份／外部 provider／手機路徑。

若 Issue 修的是「GitHub 排程或 CI 是否真的會觸發」，仍需該自動觸發路徑的執行證據；本機測試只能補產品測試，不可替代觸發修復。已成功的相關產品 SHA 若之後只有 audit/docs 變動，不自動判產品回歸；新 CI admission failure 與產品測試失敗分開記錄。

多 repo 同時零步驟失敗時先調查共用原因，不推測帳單、額度或 YAML。共用原因確認後用一個根因追蹤加受影響清單；各 repo 特有的測試遺漏仍可獨立保留。缺證據可阻止 CLEAN，但不自動創造 P0/P1 缺陷。兩輪完整 persona CLEAN，不等於每一張小工單都要兩次 CI、50 人全量或真人實驗才能結案。

## 5. 已有 Issues 的漸進整理

優先讀現行分支、全文／完整 comments、相關 PR/branch、可用 owner/run/status。遵守 `github-issue-lock:v1`，有效 lease 或活躍實作者存在時不重寫 scope。取得／讀回驗證鎖，寫入後 release；不刪歷史 marker。共用檔案用新讀取的 blob SHA，衝突則重讀整合或跳過。

對尚未實作且過大的工單，保留核心問題與原始來源，移除不必要阻塞依賴，將大型提案保留為非阻塞研究；降級時記錄原級、新級與證據。不是修好了就不能寫 FIXED，不能只為 CLEAN 關單或 not_planned。

不大量關閉、不自動重開已被使用者合理拒絕的方向。舊報告保留作歷史，當前 umbrella/index 引用新的分流決策，避免下一輪依舊摘要把工單恢復成過大版本。

## 6. 成功與限制

紀錄本輪已確認、證據不足、重複、縮範圍、分級修正與寫入阻塞的實際數量，讓後續可檢查開單品質。成功是有效修復、較少誤報／返工與核心流程改善，不是新 Issue 或報告數量。不得編造節省時間、通過率或已部署控制。

產生端會標示實作資格；外部／本機 worker 若未讀取並執行此規則，不能宣稱已被技術性阻擋。修改 worker 程式、CI、部署或啟停其他流程需另有適當授權，本次不做。
